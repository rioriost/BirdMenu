# BirdMenu 設計・コードレビューと修正プラン

レビュー日: 2026-09-16

対象: `43e593bc93b693b83531f5d7ef8359913c712c6c` / バージョン 1.2.1

レビュー: GPT-6 Astra

状態: レビュー時点では実装未変更。後続の依頼により 1.2.2 で下記の対応を実装した。指摘の行番号はレビュー対象コミットに対応する。

## 1.2.2 の実装対応

- T1: 有効な新規ブロックによって更新する 180 秒の無進捗期限、15 秒から最大 60 秒の再送バックオフを導入。旧 120/300 秒の進捗非依存の打ち切りを撤廃し、40 分の全体安全上限を維持。
- T2: CoreBluetooth に依存しない状態機械を導入し、通知受信、書き込み応答、保存完了を分離。FFF3 書き込み待ちの遅延ブロックを保持し、書き込みは単一 in-flight に制限。
- T3: 対象を絞った一時的な接続障害に最大 2 回の自動再接続を追加。毎回別ファイルに保存して新しい取得として開始し、異なるセッションのブロックを混ぜない。デバイス仕様未確認のクロスセッション再開は実装していない。
- T4: 完全な raw/CSV の保存完了後にのみ 04 を送信。受信中のチェックポイント、キャンセル時の保存、デバイス側の終了未確認の警告を追加。保存処理は専用キューで実行。
- T5/T6: 欠損判定とデコードの有効ブロック集合を共通化。長さ・件数・番号範囲・通知元を検証し、不正な重複による上書きを防止。0 件の正常結果にも対応。
- A1〜A4: 二重取得と古い完了イベントを排除し、保存済みセンサー選択を維持。平均の鮮度に最古の構成要素を使用。センサーを選択して非同期にグラフを生成し、別センサーの混在を防止。
- 追加対応: 再送要求を最大 91 番号ずつに分割し、書き込み可能長と backpressure を確認。探索・初期化・応答待ちの期限、キャンセルと終了待ち、通常ログの失敗理由を追加。

非公開プロトコルの実機挙動を新たに断定したものではない。弱電波の実機条件や 04/05 のファームウェアごとの効果は、引き続き実機で確認する必要がある。

## 結論と前提

**修正が必要。タイムアウト値を延ばすだけでは、不安定な通信での転送中断を十分に解決できない。**

ITH-11-B の履歴取得には、短い無通信期間からの再試行打ち切り、進捗に関係しない期限、遅延通知と書き込み応答の取り違え、切断時の即時終了がある。これらは報告された症状を説明できるコード上の経路である。ただし、今回の実際のエラー文、失敗時の raw JSON、BLE トレースは提示されていないため、個別の発生事例の原因はまだ特定していない。

レビュー対象は Swift ソース、既存のプロトコル関連テスト、UI・設定・起動処理、履歴エクスポート、ビルド設定、履歴取得の変更履歴。実機での無線品質別の再現や、非公開プロトコルのコマンド効果の再確認は、このレビューの範囲には含まない。

既存設計のうち、ブロック番号による重複排除・欠損検出、FFF3 による再送要求、04 送信前の件数・時刻検証、失敗時の raw JSON 保存、FFF9 へ書き込まない方針は維持する。全面的な書き直しではなく、転送の状態管理と保存順序を中心に修正する。

優先度は P1 を次の信頼性修正版での対応対象、P2 を通常の修正対象とする。

## 転送に関する指摘

### T1 — P1: 「遅いが進んでいる転送」を終了する期限設計

根拠:

- `Sources/BirdMenu/InkbirdScanner.swift:313-314,655-681,704-733,748-764,929-935`
- `Sources/BirdMenu/InkbirdITH11BHistoryProtocol.swift:35-99`
- `Sources/BirdMenu/InkbirdScanner.swift:640-643`

現在の ITH-11-B の主な期限は次のとおり。

| 期限 | 現在の値 | 満了時の動作 |
| --- | --- | --- |
| 履歴通知の無通信期間 | 5 秒 | 欠損ブロックの再送処理へ移る |
| 進捗なしの再送 | 連続 3 ラウンド | 取得を失敗終了する |
| 再送コマンド 03 の実行時間 | 120 秒 | 受信の進捗に関係なく失敗終了する |
| 欠損回復の経過時間 | 最初の再送判断から 300 秒 | 次の回復判断時、進捗があっても失敗終了する |
| 初回コマンド 01 の実行時間 | 1,800 秒 | 進捗に関係なく失敗終了する |
| 接続開始からの操作全体 | 2,400 秒 | 進捗に関係なく失敗終了する |

5 秒だけで直ちに失敗するわけではない。しかし書き込み応答が速く、再送でも新しいブロックが来ない場合、無通信開始から約 5 秒で初回再送、約 10 秒と 15 秒で次の再送、約 20 秒で打ち切りとなる。再送開始後の猶予は約 15 秒しかない。書き込み待ちやメインループの遅れはこの時間に加算される。

また `MissingBlockRecoveryTracker.startedAt` は進捗で更新されない。最初の再送から 301 秒の時点で受信ブロックが増えていても、未完了なら `timedOut` となる。既存の `timesOutMissingBlockRecoveryEvenWhenProgressContinues` も、この方針を明示的に固定している。

**修正方針:** コマンド応答待ち、有効な新規ブロックの無進捗期間、操作全体の安全上限を分ける。新規有効ブロックで無進捗期限を更新し、重複・無関係な通知では更新しない。再送は連続回数だけでなく経過時間とバックオフで管理する。全体の上限は残し、到達時は保存済みデータと終了理由を明示する。具体的な待機秒数は実機の通知間隔・再送応答時間から決める。

### T2 — P1: 遅延通知でブロックが失われ、書き込み応答待ちも飛ばされる

根拠:

- `Sources/BirdMenu/InkbirdScanner.swift:508-568,655-681,744-770`
- `Sources/BirdMenu/InkbirdHistoryExport.swift:330-343`

受信パケットには、その内容ではなく、受信時の `currentAttempt.command.name` を付けている。一方、履歴デコーダーは `ith11b_history_command_01` / `03` と付いたパケットだけを採用する。

再現条件:

1. 01 または 03 の受信が 5 秒途切れる。
2. FFF3 への欠損一覧書き込みを開始し、その応答を待っている。
3. 元の転送から遅れた正しい FFF6 のブロックが届く。

このブロックは `ith11b_missing_blocks_round_N` と記録されるため、保存した raw には存在しても受信済みブロックとして認識されない。同じデータでも 01 として記録した場合は認識される。

さらに、この通知は `quietTimeout = 0` のタイマーを起動する。`handleQuietTimeout()` は非コンテンツコマンドなら次へ進むため、FFF3 の書き込み応答前に 03 を送信し得る。同様に 04/05 待ちでも遅延通知が状態を進め得る。`didWriteValueFor` は応答元と待機中の書き込みを対応付けず、現在のコマンドの `finishesOnWrite` を見るだけなので、遅れた応答を別コマンドの完了として扱う経路もある。

**修正方針:** 生パケットの「到着時コマンド」と、プロトコル上のパケット種別を分離する。同じ取得セッションの有効な FFF6 ブロックは、再送要求の書き込み待ちでも受け付ける。書き込み完了と通知受信を独立したイベントにし、通知だけでは書き込み待ちを完了させない。応答あり書き込みは単一 in-flight とし、対応する応答を消費するまで次の書き込みを開始しない。

### T3 — P1: 一時切断・通信エラーを回復せず終了する

根拠:

- `Sources/BirdMenu/InkbirdScanner.swift:389-403,499-514,557-560,572-583`
- `Sources/BirdMenu/InkbirdScanner.swift:69-85`

完了後の想定された切断以外は、`didDisconnect` から即座に `fail()` となる。GATT 読み取り・通知設定・書き込みのエラーも原則として同じである。失敗時の保存後、操作オブジェクトを破棄するため、取得済みブロックを引き継いだ再接続や再開はできない。

これは通信が悪い場合の中断を直接説明する。ただし、実際に一時切断したのか、T1 の期限が先に満了したのかは、エラーとログの照合が必要。

**修正方針:** 一時的な接続障害と、認証・非対応属性・不正な必須応答などの継続不能なエラーを分類する。一時障害には回数・時間上限つきの再接続を設け、受信済み情報は保存する。ただし、再接続後に同じ履歴スナップショットを取得していると確認できる場合だけ再利用する。ヘッダーの件数一致だけを根拠に別取得のブロックを混ぜない。

再接続でデバイス側のセッションが初期化される場合や、同一性を確認できない場合は、部分データを保持したまま別の取得として扱う。04/05 を無条件に再送する実装にはしない。

### T4 — P1: デバイスへの完了通知よりローカル保存が後

根拠:

- `Sources/BirdMenu/InkbirdScanner.swift:621-639,809-833,939-960`
- `Sources/BirdMenu/InkbirdHistoryExport.swift:65-120`
- `README.md` の「取得済みでないレコードが返ることがある」という説明

現在は全ブロックをメモリー上で検証してから 04 と 05 を送り、その後で初めて正常系の raw JSON / CSV を保存する。

04/05 によってセンサーの同期済み位置が進む場合、その後のアプリ終了・クラッシュ・保存先エラーで、Mac に未保存かつ次回再取得できないデータが発生し得る。失敗時の raw 保存は通常のエラーには有用だが、プロセス終了や継続するディスク障害への保証にはならない。

**確定しているのは保存順序の問題であり、04/05 が特定ファームウェアで削除やカーソル更新を行うことを今回断定したものではない。** その効果と再実行可能性は実機トレースで確認する。

**修正方針:** 完全な raw と再デコードに必要なメタデータを、04 より前にローカルへ原子的に保存する。保存できなければ 04 に進まない。取得完了、ローカル保存完了、デバイスへの完了通知、セッション終了を別状態にする。保存後に接続が切れた場合は、履歴の保存成功とデバイス側状態の不確定を分けて表示する。

### T5 — P1: 不完全ブロックと範囲外ブロックの検証が不整合

根拠:

- `Sources/BirdMenu/InkbirdITH11BHistoryProtocol.swift:148-180`
- `Sources/BirdMenu/InkbirdHistoryExport.swift:214-274,326-369`
- `Sources/BirdMenu/InkbirdScanner.swift:704-715`

ブロックの受信済み判定は番号の存在で決まり、中身の不足を欠損扱いにしない。一方で、完了判定用のデコード件数には期待範囲外の番号のブロックも含まれる。

具体例:

- ヘッダーは 90 件、期待ブロックは 1 と 2。
- ブロック 1 は 44 件だけ有効で残りがゼロ、ブロック 2 は 45 件。
- 受信番号は揃っているので欠損一覧は空だが、件数は 89。そのまま失敗し、不完全なブロック 1 を再送対象にできない。
- ここに期待範囲外のブロック 3 の 1 件があると、総件数 90 で完了し、異なるブロックを混ぜた履歴が出力される。

無線品質の低下がこのような内容を必ず作るわけではない。これは遅延・混在・予期しないパケットに対する検証の欠陥であり、誤った履歴への完了通知を防ぐために修正する。

**修正方針:** 正規化した有効ブロック集合を一つ持ち、件数・欠損・デコードの全てに同じ集合を使う。セッション、通知元、期待番号範囲、ペイロード長、非最終ブロックと最終ブロックそれぞれの必要件数を検証する。不完全なブロックは再送対象とし、有効な既存ブロックを不正な重複で上書きしない。生パケットは診断用に別途保持する。

### T6 — P2: 履歴が 0 件でもエラーになる

根拠:

- `Sources/BirdMenu/InkbirdITH11BHistoryProtocol.swift:30-32,167-180`
- `Sources/BirdMenu/InkbirdScanner.swift:621-634,851-872`

0 件のヘッダーはブロック集合としては完了になり、04 前の `records.count == expectedRecordCount` も成立する。しかし最後の `validateSuccessfulHistoryFlow()` は `records.isEmpty` を失敗扱いにする。正常な「未取得履歴なし」をデコード失敗として報告する。

**修正方針:** 検証済みの 0 件ヘッダーを正常な空結果として扱う。ヘッダー未受信・不正ヘッダー・正の件数なのに空というエラーとは区別する。0 件のセッション終了手順も実機で確認する。

### 追加の設計制約・要確認事項

- **92 ブロック以上の欠損に対応できない。** `missingBlockRequest` は 182 バイトに収まる 91 番号までだが、呼び出し元は全欠損を一括で渡すため、92 個以上で要求を組み立てられず終了する。根拠は `InkbirdITH11BHistoryProtocol.swift:201-213` と `InkbirdScanner.swift:736-741`。対象機の最大履歴量がこの条件に達するかは未確認。分割再送を行うなら、デバイス側の FFF3/03 のバッチ動作と接続の書き込み可能長を確認する。小さい履歴しか扱えない場合も、その上限はヘッダー受信時に明示する。
- **UI と BLE のメインキュー共有。** BLE の delegate queue は `.main` (`InkbirdScanner.swift:29-32`)。グラフ生成はメインアクターから CSV 走査・PNG 生成を同期実行する (`SettingsWindowController.swift:139-144`)。実行中は BLE コールバックとタイマー処理も遅れる。今回の転送エラーの原因と断定はしないが、長いファイル処理は状態管理から分離する。
- **キャンセル・終了時の保存保護がない。** 取得中でも終了メニューが即時にアプリを終了する (`StatusMenuController.swift:182-183`)。長時間転送に対応する変更と一緒に、キャンセル時の部分保存、終了時の保存・終了判断を追加する。
- **接続・初期探索の応答待ちが粗い。** 個別の接続・探索・初期読込の期限がなく、応答が来ない経路では操作全体の 40 分上限まで待ち得る。必須属性と任意の診断用属性を分け、段階別の待機とエラー表示を設ける。
- **README の実装説明が古い。** FFF8 がない場合を読み取り専用と説明しているが、現実装は ITH-11-B で FFF3/FFF4/FFF7 に書き込む。実装修正時に、この経路、再試行・保存・空結果の仕様を更新する。

## 修正プラン

### 1. 転送状態の分離と回帰ケースの固定

対象: `InkbirdScanner.swift`、`InkbirdITH11BHistoryProtocol.swift`、履歴関連テスト。

現在の `HistoryFetchOperation` は CoreBluetooth 呼び出し、タイマー、コマンド状態、受信分類、検証、ファイル保存をまとめて持っている。純粋関数のテストだけでは、通知と書き込み応答の順序の問題を捕捉できない。

接続処理は既存の Scanner に残し、履歴取得の状態遷移だけを小さなテスト可能な単位へ分離する。時計・タイマー・BLE イベント・保存成功/失敗を入力できる境界を作り、実際に数分待ったり実機を接続したりせずに順序と期限を検証できるようにする。新しいフレームワークは導入しない。

状態は少なくとも接続、初期化、ヘッダー待ち、本文受信、再送一覧書き込み待ち、再送受信、ローカル保存、完了通知、終了を区別する。終端結果は一度だけ通知し、別デバイスや終了済み接続のイベントが次の取得を進めないようにする。

### 2. T2・T5 の受信／書き込み整合性を修正する

期限を緩和するより先に、受信したブロックを正しく保持し、正しい応答でだけ状態を進めるようにする。

- 受信パケットの分類をコマンド文字列から切り離す。
- 検証済みブロック集合を完了判定とデコードの共通の入力にする。
- 再送要求の応答待ちでも、同一セッションの遅延ブロックを受け取る。
- 通知による 0 秒タイマーで書き込み完了を代替しない。
- 書き込み応答を直列管理し、04/05 へ早送りしない。
- 0 件を正常結果として扱う。

### 3. T1 の待機・再試行ポリシーを修正する

応答待ちと無進捗時間を分離する。受信したバイト数ではなく、有効な新規ブロックの増加を進捗とする。経過時間には壁時計変更の影響を受けない単調時計を使う。

無進捗の猶予、再送バックオフ、再接続の上限、操作全体の安全上限を一か所で定義する。安全上限まで無条件に待たせるのではなく、停止理由と部分保存状態を明示する。T1 の現行挙動を固定したテストも新しい仕様に変更する。

### 4. T4 の保存順序と終了時の扱いを修正する

保存先への書き込み可否を早期に確認する。ただし事前確認だけには頼らず、04 前の保存完了を状態遷移の必須条件とする。

取得セッションを識別できる保存先を確保し、デバイス ID、ヘッダー、記録間隔、時刻設定の根拠、受信ブロック、取得段階を保持する。完全な raw を保存してから 04/05 を実行する。CSV 生成失敗と raw の保存成功を区別して報告する。

転送途中でも適切な区切りで raw と進捗を保存する。不完全なデータを、時刻の欠損を詰めた「完全な CSV」として出力しない。キャンセル・終了・保存エラーでは取得段階に応じた結果を返し、保存失敗を隠さない。

### 5. T3 の再接続を段階的に導入する

ここはデバイスプロトコルの確認に依存する。まず、一時切断後のヘッダー、再送要求、01、04、05 の挙動と、履歴スナップショットを識別できる情報を実機で確認する。

確認できた条件だけで、保存済みブロックを再利用する限定的な再開を実装する。確認できない場合は、取得を分離した安全な再試行にとどめる。異なるスナップショットを混ぜて見かけ上完了させない。再接続前後に残ったコールバックや未完了の書き込みは、接続終了待ちと単一 in-flight 管理で次の操作から隔離する。

### 6. UI・診断・説明を揃える

取得件数/期待件数、受信ブロック数、経過時間、再送中・再接続中・保存中を表示する。キャンセルを可能にし、二重取得は UI と Scanner の両方で防ぐ。グラフ生成や保存の長い処理は、BLE 状態管理を同期的に止めない形にする。

通常ログには開始、状態遷移、失敗理由、経過時間、最終有効ブロックからの時間、欠損番号、再試行数、CoreBluetooth のエラードメイン/コードを残す。生の測定値・パケットは従来の Debug Logging に限定し、外部送信は追加しない。

A2〜A4 は転送修正とは別の小さな変更として扱う。README の説明も実装と一致させる。

## 受け入れ条件

仮想時計とイベント列による回帰テストでは、時間と出力を具体的に確認する。

| 条件 | 期待する結果 |
| --- | --- |
| 接続を維持したまま通知が 6 秒・12 秒・30 秒遅れる | 合意した無進捗猶予内なら、単に 5 秒を超えたことや再送回数だけで終了しない。遅延ブロックも採用する。 |
| 03 の受信が 121 秒、欠損回復が 301 秒を超え、有効な新規ブロックが継続する | 旧 120/300 秒の期限だけを理由に終了しない。新しい安全上限は別に検証する。 |
| 重複・無関係な通知だけが続く | 進捗と誤認せず、定義した無進捗期限で保存して明示的に停止する。 |
| FFF3 書き込み待ちに正しい FFF6 が届く | ブロックを保持する。書き込み応答前に次の書き込みへ進めない。 |
| 通知が書き込み応答に先行する、04/05 待ちに遅延通知が届く | コマンドを飛ばさず、対応する完了条件だけで遷移する。 |
| 90 件の履歴に 44 件 + 45 件のブロックが届く | 不完全なブロックを再送対象にする。範囲外ブロックを足して完了扱いにしない。 |
| 有効なブロックの後に不正な同番号ブロックが届く | 有効な内容を失わず、不正なパケットの診断情報を残す。 |
| 正常な 0 件ヘッダー | 「新しい履歴なし」として完了し、デコード失敗にしない。 |
| 保存失敗、04 前後の切断、キャンセル、アプリ終了 | 未保存のまま完了通知しない。保存結果とデバイス側同期結果を区別する。 |
| 部分取得後に再接続、同件数だが内容が異なる取得を検出 | 同一スナップショットと確認できないデータを混ぜない。 |
| 91 / 92 個以上の欠損 | 対応機の仕様に沿った分割回復、または明確な対応上限のエラーとなる。 |
| メニューを再表示・再選択、終了済み接続の遅延イベント | 二重取得や誤った状態遷移がなく、完了通知は一度だけ。 |
| 選択済みセンサーより別センサーを先に発見 | 保存済み選択を維持する。 |
| 片方のセンサーが古い、別センサーに同時刻の CSV がある | 鮮度を偽装せず、別センサーのデータを上書き・混合しない。 |

最後に実機で、通常距離・弱い電波・一時切断・長い履歴のそれぞれについて、期待件数との一致、欠損の解消、保存ファイルの再デコード、04/05 と保存の順序を確認する。既存の広告取得、通常の履歴取得、FFF8 経路、未知デバイスへの読み取り専用方針を退行させない。

**推奨する実施順は、状態分離 → 通知／応答の整合性とブロック検証 → 待機ポリシー → 保存順序 → 実機仕様を踏まえた再接続。タイムアウトの一律延長だけを先行リリースしない。**
